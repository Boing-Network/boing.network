# Storage-tree v2 (full-key routing) — activation and migration notes

**Status:** implemented, **OFF by default**. Nothing changes on any chain until every node is started
with the same `BOING_STORAGE_TREE_V2_ACTIVATION_HEIGHT` (or `--storage-tree-v2-activation-height`).

## The problem

The state root commits to each contract's storage through a per-contract sparse Merkle tree. That tree
routes on only the **first 64 bits (8 bytes)** of the 32-byte storage key. Two slots that share those 8
bytes land in the same bucket and **only the smallest key of the bucket is committed**. Consequences:

- Changing the value of any non-smallest slot in a bucket does **not** change the state root.
- A storage proof (`prove_storage`) for such a slot can never verify against the root.
- Contracts that use small integers or structured keys (`mapping[id]` with a common prefix) hit this
  naturally; an adversary can also choose keys to hide writes from the root.

Slot *values* are still stored and executed correctly (the VM reads the real map); only the **commitment**
is incomplete. The global account tree is unaffected (keys are public keys / hashes).

## The fix

From the activation height `H`, every per-contract storage tree routes on **all 256 key bits**
(`DEEP_MAX_DEPTH = 256`). Everything else is identical:

| Rule | Legacy (64) | v2 (256) |
|---|---|---|
| Empty subtree | `Hash::ZERO` | same |
| Subtree with one entry | `BLAKE3(key ‖ value_hash)` | same |
| Subtree with ≥ 2 entries | `BLAKE3(left ‖ right)` | same |
| Entries sharing every routed bit | smallest key wins | impossible (distinct keys diverge) |

Because single-entry subtrees are collapsed, the cost scales with occupied paths, not with 256. The
global account tree stays at 64 bits. Leaf values (`BLAKE3(value)`) and the account leaf layout are
unchanged.

Where it plugs in: `StateStore::state_root_at_height(height)` (used by both the block producer and
`validate_block`). When `height >= H` the storage trees are rebuilt once at depth 256 and then
maintained incrementally; for `height < H` (including rewinds) they use depth 64. With no activation
configured the call is exactly `state_root()`.

## Why it cannot fork the live chain while inactive

- The default is `None`; the code path for `height < H` / no config is byte-for-byte the legacy
  algorithm (`legacy_state_root_is_pinned` pins a golden root generated by the pre-v2 binary, and the
  same test file passes against the old code).
- No wire, RPC or on-disk format changes. Persistence stores raw slots, not trees.
- Blocks before `H` validate exactly as before, so mixed old/new binaries agree until `H`.

## Activation procedure (mainnet or testnet)

1. **Ship the binary first.** Release the build containing this change to *all* validators and RPC
   nodes with the env var **unset**. Confirm every validator runs it (`boing_clientVersion`).
2. **Pick `H`.** Choose a height comfortably in the future (≥ 24 h of blocks on the live chain; more
   if validators are slow to roll). Announce `H` to every operator.
3. **Rehearse.** On a throw-away devnet, start from a copy of the current state with
   `BOING_STORAGE_TREE_V2_ACTIVATION_HEIGHT=<devnet_height+20>` on all nodes and confirm blocks keep
   committing across `H`. Never rehearse against live nodes.
4. **Roll out the config.** Set `BOING_STORAGE_TREE_V2_ACTIVATION_HEIGHT=H` on every validator and RPC
   node and restart (staggered) *before* the chain reaches `H`. A node that does not set it will
   compute the legacy root at `H` and **reject the first v2 block** (`InvalidStateRoot`), i.e. it stops
   following the chain until it is restarted with the value.
5. **Verify.** At `H` all validators should keep voting. After `H`,
   `boing_getContractStorage` is unchanged; storage proofs for previously-colliding slots now verify.
6. **Never lower or remove `H` afterwards.** Restarts must keep the same value; a node restarted
   without it will diverge at `H`.

### Rollback

Before `H`: unset the variable and restart (no state was changed). After `H`: not supported; the
legacy rule would reject every post-`H` block. Plan activation as one-way.

### One-time cost at activation

The first `state_root_at_height(H)` rebuilds every contract storage tree at depth 256 (same order of
cost as a cold `state_root`; see `docs/PERFORMANCE.md`). It happens once per node at `H` (or at
startup if the node boots at/after `H`).

## Migration notes for tooling

- **Discovery:** `boing_getNetworkInfo` and `boing_health` publish `storage_tree_v2_activation_height` (integer, or `null` when this node has no activation configured, which is the default). Tooling that recomputes storage roots should use 256-bit routing exactly when `height >= storage_tree_v2_activation_height`. The value is the node's configuration (not persisted), so check that all nodes report the same number before and after rollout.

- **boing.observer / indexers** that recompute storage roots must switch to 256-bit routing for
  heights `>= H`. Roots before `H` keep the 64-bit rule.
- **Light clients** that verify `prove_storage` proofs: the proof format is unchanged (list of
  `{sibling_hash, path_bit}` from root to leaf); at `H` the lists simply get longer for deep paths.
- `MerkleProof::verify` folds the siblings leaf → root. Earlier builds folded them in the wrong order for
  proofs with more than one step; any verifier ported from that code must be fixed.
- Contract authors need no change.
